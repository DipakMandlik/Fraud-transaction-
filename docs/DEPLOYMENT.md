# Deployment Guide

This guide covers running the Fraud Detection Platform with Docker Compose (the supported path for demos and
evaluation), running each service locally without containers, the full environment variable reference, and
what to change before putting the platform in front of production traffic.

## Architecture recap

The stack has four runtime pieces, all defined in `docker-compose.yml`:

| Service | Image / Build | Purpose |
|---|---|---|
| `postgres` | `postgres:16-alpine` | System of record — transactions, customers, alerts, rules, investigations, sessions |
| `redis` | `redis:7-alpine` | Pub/sub transport for live events consumed by the `/ws/events` WebSocket |
| `backend` | built from `./backend` (`backend/Dockerfile`) | FastAPI app (REST API + WebSocket), APScheduler background jobs, DB seeding |
| `frontend` | built from `./frontend` (`frontend/Dockerfile`) | React/Vite SPA, built and served as static files by Nginx, which also reverse-proxies `/api` and `/ws` to the backend |

## Docker Compose deployment

### Prerequisites

- Docker and Docker Compose v2.

### Bring the stack up

```bash
docker compose up --build
```

- Frontend (Nginx-served SPA): **http://localhost:3000**
- Backend + interactive Swagger docs: **http://localhost:8000/docs**
- PostgreSQL: **localhost:5432** (user/password/db: `fraud` / `fraud` / `frauddb`)
- Redis: **localhost:6379**

### Services, ports, and startup order

- **`postgres`** — exposes `5432:5432`, persists data to the named volume `postgres_data`. Has a
  `pg_isready` healthcheck (5s interval, 10 retries).
- **`redis`** — exposes `6379:6379`. Has a `redis-cli ping` healthcheck (5s interval, 10 retries).
- **`backend`** — built from `./backend`; exposes `8000:8000`. `depends_on` both `postgres` and `redis` with
  `condition: service_healthy`, so it will not start until both healthchecks pass. Its own healthcheck calls
  `GET http://localhost:8000/api/health` from inside the container (10s interval, 10 retries). Environment is
  seeded from `backend/.env.example` via `env_file`, with `DATABASE_URL`, `REDIS_URL`, and `CORS_ORIGINS`
  overridden in `docker-compose.yml` to point at the `postgres`/`redis` service hostnames (Compose's internal
  DNS) instead of `localhost`.
- **`frontend`** — built from `./frontend`; exposes `3000:80` (host 3000 → container Nginx port 80).
  `depends_on: backend` (start-order only — Compose does not wait for the backend's healthcheck here).

On backend startup (`app/main.py` `lifespan`), the app runs database seeding (`app.seed.run_seed`, idempotent —
safe to run on every boot) and then starts the in-process APScheduler background scheduler
(`app.scheduler.start_scheduler`) before accepting traffic.

### Frontend routing (Nginx)

`frontend/nginx.conf` serves the built SPA from `/usr/share/nginx/html` with an SPA fallback
(`try_files $uri $uri/ /index.html`), and reverse-proxies:

- `/api/` → `http://backend:8000/api/`
- `/ws/` → `http://backend:8000/ws/` (with `Upgrade`/`Connection` headers set for WebSocket upgrade and a
  3600s `proxy_read_timeout` to keep long-lived socket connections open)

## Environment variable reference

All configuration is read by `backend/app/config.py` (a Pydantic `BaseSettings` model) from `backend/.env`
(copy from `backend/.env.example`; the Compose file also loads `backend/.env.example` directly via `env_file`
for the `backend` service). Values below are the built-in defaults.

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | `postgresql+psycopg2://fraud:fraud@localhost:5432/frauddb` | SQLAlchemy connection string. Overridden in Compose to `...@postgres:5432/frauddb`. |
| `REDIS_URL` | `redis://localhost:6379/0` | Redis connection string for pub/sub events. Overridden in Compose to `redis://redis:6379/0`. |
| `SECRET_KEY` | `change-me-in-production` | Application secret (session/token signing). **Must** be changed for any non-local deployment. |
| `ADMIN_USERNAME` | `admin` | Seeded default administrator login. |
| `ADMIN_PASSWORD` | `admin` | Seeded default administrator password. **Must** be changed before any real-world exposure. |
| `CORS_ORIGINS` | `http://localhost:5173,http://localhost:3000` | Comma-separated list of allowed browser origins; parsed into `cors_origins_list` and passed to FastAPI's `CORSMiddleware`. |
| `TXN_MIN_INTERVAL_SECONDS` | `2` | Minimum random delay (seconds) between synthetic "normal" transactions generated by the background scheduler. |
| `TXN_MAX_INTERVAL_SECONDS` | `5` | Maximum such delay. |
| `FRAUD_INJECTION_MIN_SECONDS` | `30` | Minimum random delay (seconds) between injected fraud scenarios. |
| `FRAUD_INJECTION_MAX_SECONDS` | `60` | Maximum such delay. (A separate, tighter 20–30s window is used automatically when "Demo Mode" is toggled on via `POST /api/demo/mode` or `POST /api/settings`-adjacent controls — this is an in-memory runtime override, not an env var.) |
| `FRAUD_RATIO` | `0.10` | Target fraction of generated activity that should be fraudulent, used by the fraud injector/generator. |

`Settings.model_config` sets `extra="ignore"`, so unrecognized variables in the `.env` file are silently
ignored rather than raising an error.

## Local (non-Docker) setup

Requires PostgreSQL and Redis reachable from your machine (e.g. installed locally, or run just those two
services via `docker compose up postgres redis`).

### Backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # adjust DATABASE_URL / REDIS_URL if your Postgres/Redis aren't on localhost defaults
uvicorn app.main:app --reload
```

Key backend dependencies (`backend/requirements.txt`): FastAPI 0.111, Uvicorn 0.30 (`[standard]`),
SQLAlchemy 2.0, psycopg2-binary, Pydantic 2.7 / pydantic-settings 2.3, APScheduler 3.10, redis-py 5.0,
passlib[bcrypt], itsdangerous, python-multipart, Faker (for seed data generation).

The backend listens on `http://localhost:8000` by default, with Swagger UI at `/docs`.

### Frontend

```bash
cd frontend
npm install
npm run dev
```

The Vite dev server runs on `http://localhost:5173` and proxies `/api` and `/ws` requests through to
`http://localhost:8000` (see `frontend/vite.config.ts`), matching the same-origin behavior Nginx provides in
the containerized deployment.

### First-run checklist

- PostgreSQL and Redis are reachable at the URLs configured in `backend/.env`.
- The `uvicorn` startup log shows seeding output (seeding is idempotent — safe to run every boot, and the rule
  catalog is re-synced each startup).
- `GET /api/health` returns `{"status": "ok", "database": true, "redis": true}`.
- Sign in with the seeded `admin` / `admin` credentials (or whatever `ADMIN_USERNAME`/`ADMIN_PASSWORD` are set
  to) and confirm dashboard counters move on their own — that's the background transaction generator running.

## Live free-tier deployment: GitHub Pages + Render + Neon

This is a second, independent deployment recipe for putting a real, publicly reachable instance online at zero
cost — useful for demos, portfolios, and stakeholder walkthroughs where cloning and running the stack locally
isn't practical. It does **not** replace Docker Compose as the primary supported deployment; it's an additive
option.

GitHub Pages only serves static files, so it hosts the frontend only. The backend (FastAPI, PostgreSQL, Redis,
and the APScheduler background jobs) runs on separate free-tier services that GitHub Pages calls over the
network.

### Architecture

```
GitHub Pages (static)              Render (free Web Service)         Neon (free Postgres)
  React/Vite build          <--->    FastAPI + Uvicorn                 (permanent free tier)
  https://<user>.github.io/          + APScheduler jobs        <--->
    <repo>/                          + Render free Key Value
                                        (Redis-compatible, private
                                        network — no separate account)
```

- **Frontend**: built and deployed automatically by `.github/workflows/deploy-pages.yml` on every push to
  `main`, published via GitHub Pages.
- **Backend**: Render free Web Service, deployed straight from `backend/Dockerfile` via the `render.yaml`
  Blueprint at the repo root.
- **Redis**: a Render free **Key Value** instance (Render's current name for its Redis-compatible offering),
  reached over Render's private network — no external Redis account needed, since this app only uses Redis as a
  pub/sub transport with nothing persisted (`backend/app/services/event_bus.py`).
- **Database**: Neon free-tier Postgres, chosen over Render's own free Postgres because Render's free database
  expires after 30 days and must be manually recreated, while Neon's free tier is a standing allowance.

### One-time setup (manual — requires your own accounts)

1. **Neon**: create a free account at neon.tech → new project → copy the pooled connection string (it already
   includes `?sslmode=require`).
2. **Render**: create a free account at render.com → "New +" → "Blueprint" → connect this GitHub repository.
   Render reads `render.yaml` automatically and provisions the web service plus the Key Value instance. When
   prompted, fill in:
   - `DATABASE_URL` → the Neon connection string from step 1
   - `ADMIN_USERNAME` / `ADMIN_PASSWORD` → **do not leave these as `admin`/`admin` once the URL is public** —
     this is a real, shared, publicly reachable instance; anyone with the URL can act as whoever holds these
     credentials
   - `CORS_ORIGINS` → your GitHub Pages **origin only**, e.g. `https://<your-username>.github.io` (no trailing
     path — CORS matches scheme+host+port, not the `/<repo>/` subpath)

   `REDIS_URL` and `SECRET_KEY` are wired automatically by the Blueprint (`fromService` / `generateValue`).
   Deploy, then copy the resulting `https://<service>.onrender.com` URL.
3. **GitHub repository variables** (Settings → Secrets and variables → Actions → Variables): set
   - `VITE_API_BASE_URL` = `https://<service>.onrender.com/api`
   - `VITE_WS_BASE_URL` = `wss://<service>.onrender.com`
4. **GitHub Pages**: Settings → Pages → Source → "GitHub Actions" (one-time toggle).
5. Push to `main` (or re-run the `Deploy Frontend to GitHub Pages` workflow) to trigger the first deploy.

### What "live" actually means on the free tier

- Render's free web service **sleeps after ~15 minutes with no HTTP traffic** and cold-starts (typically
  30–60s) on the next request — while asleep, the background transaction/fraud generator is not running at
  all, not just running slowly. Neon's free Postgres can similarly scale to zero when idle, which can stack
  with the Render cold start on a fully idle demo. The frontend shows a "waking up the live backend" banner
  (`frontend/src/components/layout/BackendWakingBanner.tsx`, wired through a silent retry-with-backoff in
  `frontend/src/lib/api.ts`) during this window instead of surfacing a broken-looking error.
- A continuous 24/7 keep-alive ping was deliberately **not** added here: it would keep Render's instance-hours
  near its monthly free cap and, more importantly, would push Neon's compute past its free 100 CU-hour/month
  allowance roughly two weeks into the month, causing a harder, unannounced outage than the cold-start UX it
  was meant to avoid. If you want the demo to feel always-on for a specific window (a live walkthrough, an
  interview), ping `GET /api/health` a few times shortly before that window instead of continuously.
- Neon's free tier also caps storage at 0.5 GB. A generator running continuously for a long time will
  eventually approach that; periodically pruning old generated transactions (or simply re-deploying) keeps a
  long-lived free demo instance healthy.
- This is a single shared instance — every visitor sees and can act on the same data. That's expected for a
  demo, but is why rotating the admin credentials before sharing the URL matters more here than in a local or
  Docker Compose deployment.

## Production considerations

The Docker Compose setup here is built for demos, evaluation, and development — not turnkey production
hosting. Before exposing this to real traffic or real financial data, address at least the following:

- **Managed database**: Point `DATABASE_URL` at a managed, backed-up, highly-available PostgreSQL instance
  (e.g. RDS/Cloud SQL/Azure Database for PostgreSQL) rather than the single-container `postgres` service with
  a local Docker volume.
- **Managed cache/pub-sub**: Similarly, use a managed Redis (e.g. ElastiCache/Memorystore) with persistence
  and failover appropriate to your availability requirements, since Redis here also carries the live
  WebSocket event stream.
- **Process manager / workers**: Run the backend behind Gunicorn with Uvicorn workers (or an equivalent
  ASGI process manager) rather than a single bare `uvicorn app.main:app` process, for multi-core utilization
  and automatic worker restarts. See the scheduler caveat below before scaling to multiple replicas.
- **TLS termination**: Terminate TLS at a reverse proxy or load balancer (e.g. Nginx, an ALB/Cloud Load
  Balancer, or a service mesh ingress) in front of both the backend and the frontend container; the bundled
  `nginx.conf` and Uvicorn are both plain HTTP.
- **Restrict CORS**: Set `CORS_ORIGINS` to the exact production origin(s) of the frontend — the shipped
  defaults (`localhost:5173`, `localhost:3000`) are for local development only.
- **Rotate `SECRET_KEY` and admin credentials**: The default `SECRET_KEY=change-me-in-production` and
  `ADMIN_USERNAME`/`ADMIN_PASSWORD=admin`/`admin` are seed/demo values and must be replaced with strong,
  environment-specific secrets (ideally injected via a secrets manager, not committed `.env` files) before any
  non-local deployment.
- **Background scheduler is in-process and single-instance only — this is a real constraint on horizontal
  scaling.** `backend/app/scheduler.py` creates one module-level `BackgroundScheduler()` (APScheduler) and
  `backend/app/main.py`'s FastAPI `lifespan` calls `start_scheduler()` on every process startup, with no
  locking, leader-election, or "only run this on one replica" logic. Both the synthetic transaction generator
  and the fraud-injection job self-reschedule using in-memory job IDs (`next_transaction`,
  `next_fraud_injection`) local to that process. If the backend is scaled to more than one replica (multiple
  Uvicorn/Gunicorn workers, or multiple containers/pods), **each replica will run its own independent copy of
  the scheduler**, multiplying the rate of generated transactions and fraud injections rather than sharing the
  work. Before running multiple backend replicas in production, either (a) run the API and the
  scheduler as separate deployables — a single-instance "scheduler/worker" process plus horizontally-scaled,
  scheduler-disabled API replicas — or (b) add explicit leader-election / distributed-locking (e.g. a Redis
  lock) around `start_scheduler()` so only one instance ever runs the jobs. Note this simulator/generator is a
  demo-data feature; a production deployment ingesting real transactions from an external source would not
  need this scheduler at all.
- **Health checks**: Use `GET /api/health` for liveness/readiness probes. It checks both PostgreSQL
  (`SELECT 1`) and Redis (`PING`) and returns `{"status": "ok" | "degraded", "database": bool, "redis": bool}`
  — treat `"degraded"` as failing readiness (but not necessarily liveness) so the load balancer stops routing
  to an instance with a broken dependency without killing the process outright.
